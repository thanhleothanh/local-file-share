# 30. WebSocket Signaling Server for Device Discovery and Connection

**Status**: Accepted  
**Date**: 2026-06-03  
**Supersedes**: ADR-0001 (Browser-Only with No External Servers), ADR-0003 (Two-QR Code Handshake)

## Context

The current application uses a two-QR code handshake for WebRTC signaling. This requires:
- Cameras on both devices
- A two-step scanning process
- QR compression (gzip + base64) to fit SDP + ICE candidates
- External dependencies (`@zxing/browser`, `@zxing/library`, `pako`)

Users want devices on the same network to automatically discover each other and connect without scanning QR codes. The application must still work entirely on the local network with no internet dependency.

## Decision

Introduce a **WebSocket signaling server** using Express + `ws` that runs alongside the web application on the same HTTP server (port 3000). The server:

1. **Serves the built web application** (static files from `dist/`)
2. **Relays WebRTC signaling messages** (SDP offers/answers, ICE candidates) between devices
3. **Maintains a device list** of all connected WebSocket clients

The signaling server is a **pure relay** — no message validation, no connection state tracking beyond the device list. WebRTC handles authentication and integrity.

### Server Technology

- **Express** serves static files from `dist/`
- **`ws`** handles WebSocket connections on the same HTTP server
- Single `server.js` file, started with `npm run start`

### Signaling Protocol

All messages are JSON with this structure:

```json
{
  "type": "MESSAGE_TYPE",
  "from": "deviceId",
  "to": "targetDeviceId",
  "data": { ... }
}
```

**Client → Server message types:**
- `register` — Device connects with its auto-generated name
- `offer` — WebRTC SDP offer to a specific device
- `answer` — WebRTC SDP answer to a specific device
- `ice-candidate` — ICE candidate to a specific device
- `request-connect` — Device A wants to connect to Device B
- `accept-connect` — Device B accepts the connection
- `reject-connect` — Device B rejects the connection
- `disconnect` — Device is leaving

**Server → Client message types:**
- `device-list` — Updated list of all connected devices
- `offer` — Received SDP offer from another device
- `answer` — Received SDP answer from another device
- `ice-candidate` — Received ICE candidate from another device
- `connect-request` — Another device wants to connect
- `connect-accepted` — The other device accepted
- `connect-rejected` — The other device rejected
- `device-disconnected` — A device left

### Device Identification

Devices auto-generate their name from the user agent:
- Mobile phones → "Mobile #1", "Mobile #2"
- Desktops → "Desktop #1", "Desktop #2"
- Tablets → "Tablet #1", "Tablet #2"

Each device gets a UUID generated by the client and stored in `localStorage` for persistence across page refreshes.

### Connection Flow

1. Desktop runs `npm run build && npm run start` → terminal prints `Server running at http://192.168.1.100:3000`
2. Other devices type the URL → see a list of online devices with dot indicators
3. Device A clicks Device B → Device B sees accept/reject prompt
4. Device B accepts → Device A creates WebRTC offer → relayed over WebSocket → Device B creates answer → relayed back → ICE candidates exchanged → connected
5. UI shifts to per-device file transfer view

### Error Handling

- If the server goes down mid-transfer, the WebRTC connection stays alive (peer-to-peer)
- If a device disconnects from WebSocket, the server removes it from the device list and broadcasts the update
- If a connected device disconnects, the WebRTC connection closes and the UI returns to the device list

## Consequences

**Positive:**
- No camera required — works on devices without cameras
- Single-step connection — click to connect, accept, done
- No QR compression needed — WebSocket handles large payloads easily
- Simpler codebase — removed `qrHandler.js`, `qrCompression.js`, `@zxing` dependencies
- Automatic device discovery — devices appear in the list when they connect
- Familiar UX — matches patterns from Discord, Slack, etc.

**Negative:**
- Requires running a Node.js server on one desktop
- Desktop must be on and running the server for other devices to connect
- Not "zero infrastructure" — requires `npm run start` on the server machine
- WebSocket server is a single point of failure for new connections (existing connections survive server death)

## Alternatives Considered

1. **PeerJS (cloud signaling)**: Third-party WebRTC abstraction with hosted signaling server. Pros: Simpler API, no server to run. Cons: Requires internet for signaling, violates local-only privacy principle.
2. **mDNS/Bonjour**: Multicast DNS for automatic device discovery. Pros: No user interaction. Cons: Limited browser support (only Safari), requires native code or workarounds.
3. **One device as server**: The initiator runs an embedded WebSocket server. Pros: No separate process. Cons: Only works if the initiator is a desktop, complex embedded server logic.
4. **Keep QR as fallback**: Maintain QR codes for when the server is unavailable. Pros: More resilient. Cons: Contradicts user requirement to remove QR, adds significant complexity.
