# 19. WebSocket Signaling Server for Device Discovery and Connection

**Status**: Accepted  
**Date**: 2026-06-03

## Context

Devices on the same network need to discover each other and establish WebRTC peer connections. A signaling server is required to relay WebRTC SDP offers/answers and ICE candidates between devices. The server must also maintain a device list so users can see who is online and initiate connections.

## Decision

A **WebSocket signaling server** runs on port 3000, serving both the web application (static files from `client/dist/`) and WebSocket connections on the same HTTP server.

### Server Technology

- **Node.js `http` module** serves static files
- **`ws` library** handles WebSocket connections on the same HTTP server
- **TypeScript** for all server code
- Single entry point, started with `npm run start`

### Server Responsibilities

1. **Serve the built web application** (static files from `client/dist/`)
2. **Relay WebRTC signaling messages** between devices
3. **Maintain a device list** of all connected WebSocket clients
4. **Track connection state** — which devices are connected to each other
5. **Reject connection attempts** to busy devices

### Signaling Protocol

All messages are JSON with this structure:

```json
{
  "type": "MESSAGE_TYPE",
  "from": "deviceId",
  "to": "targetDeviceId",
  "data": { ... }
}
```

**Client → Server message types:**
- `register` — Device connects with its auto-generated name and persisted UUID
- `offer` — WebRTC SDP offer to a specific device
- `answer` — WebRTC SDP answer to a specific device
- `ice-candidate` — ICE candidate to a specific device
- `request-connect` — Device A wants to connect to Device B
- `accept-connect` — Device B accepts the connection
- `reject-connect` — Device B rejects the connection
- `disconnect` — Device is leaving

**Server → Client message types:**
- `device-list` — Updated list of all connected devices (with `connectedTo` field)
- `offer` — Received SDP offer from another device
- `answer` — Received SDP answer from another device
- `ice-candidate` — Received ICE candidate from another device
- `connect-request` — Another device wants to connect
- `connect-accepted` — The other device accepted
- `connect-rejected` — The other device rejected
- `device-disconnected` — A device left
- `server-disconnected` — WebSocket to server dropped (read-only mode)

### Device Identification

Devices auto-generate their name from the user agent:
- Mobile phones → "Mobile #1", "Mobile #2"
- Desktops → "Desktop #1", "Desktop #2"
- Tablets → "Tablet #1", "Tablet #2"

Users can **rename their device** (edit icon next to the name). The custom name persists in `localStorage` across sessions.

Each device gets a UUID generated by the client and stored in `localStorage` for persistence across page refreshes.

### Connection State Tracking

The server tracks which devices are connected to each other:
- Each device has a `connectedTo` field (null or the device ID of the connected peer)
- When Device A connects to Device B, the server marks both as busy
- The `device-list` broadcast includes `connectedTo` for all devices
- Clients disable the Connect button for busy devices
- If a device disconnects from WebSocket, the server clears its `connectedTo` and broadcasts the update

### Connection Flow

1. Desktop runs `npm run start` → terminal prints `Server running at http://192.168.1.100:3000`
2. Other devices type the URL → see a list of online devices
3. Device A clicks Device B → Device B sees accept/reject prompt
4. Device B accepts → Device A creates WebRTC offer → relayed over WebSocket → Device B creates answer → relayed back → ICE candidates exchanged → connected
5. UI shifts to Files tab for file transfer

### Error Handling

- If the server goes down mid-transfer, the WebRTC connection stays alive (peer-to-peer)
- Device list becomes read-only — no new connections possible
- A subtle indicator shows the server is disconnected
- Clients auto-reconnect the WebSocket in the background
- If a connected device disconnects from WebSocket, the WebRTC connection closes and the UI returns to the device list

## Consequences

**Positive:**
- No camera required — works on devices without cameras
- Single-step connection — click to connect, accept, done
- Automatic device discovery — devices appear in the list when they connect
- Server tracks busy state — prevents "device is busy" errors on the client
- Device renaming — users can distinguish their devices on crowded networks
- Familiar UX — matches patterns from Discord, Slack, etc.

**Negative:**
- Requires running a Node.js server on one desktop
- Desktop must be on and running the server for other devices to connect
- WebSocket server is a single point of failure for new connections (existing connections survive server death)
- Server is stateless beyond device list — no persistence across server restarts

## Alternatives Considered

1. **Express + `ws`**: Full web framework. Cons: Overkill for static files + WebSocket relay.
2. **PeerJS (cloud signaling)**: Third-party hosting. Cons: Requires internet, violates local-only privacy.
3. **mDNS/Bonjour**: Multicast DNS. Cons: Limited browser support, requires native code.
4. **Pure relay (no state tracking)**: Server only relays messages. Cons: Clients must independently track busy state, duplicated logic.
5. **Keep QR as fallback**: More resilient. Cons: Adds significant complexity, dead code if server is always available.
